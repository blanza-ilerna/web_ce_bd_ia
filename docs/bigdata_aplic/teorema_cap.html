El Teorema CAP (Teorema de Brewer)

El trilema fundamental del almacenamiento distribuido

Formulado por Eric Brewer en el año 2000, el Teorema CAP es la piedra angular del diseño de bases de datos y sistemas distribuidos. Establece una limitación física ineludible: en un sistema informático distribuido, es imposible garantizar simultáneamente más de dos de las tres propiedades fundamentales. Este teorema obliga a los arquitectos de Big Data a tomar decisiones estratégicas basadas en las necesidades reales del negocio.

No existe el "sistema perfecto"; existe el sistema que mejor equilibra estas tres fuerzas según el caso de uso.

Los Tres Pilares del Teorema

🎯

C - Consistencia (Consistency)

Todos los nodos del sistema ven los mismos datos al mismo tiempo. Una lectura garantiza devolver el valor de la escritura más reciente o un error.

🟢

A - Disponibilidad (Availability)

Cada solicitud recibe una respuesta (éxito o fallo), sin la garantía de que contenga el dato más actualizado. El sistema nunca deja de responder.

🏗️

P - Tolerancia a Particiones (Partition Tolerance)

El sistema continúa funcionando a pesar de que la red sufra cortes o fallos que dividan el clúster en subgrupos de nodos que no pueden comunicarse entre sí.

Seleccionando el Par Ganador

CA

Consistencia + Disponibilidad

Sistemas no distribuidos o con red infalible. Típico de bases de datos relacionales (RDBMS) clásicas.

CP

Consistencia + Partición

Sistemas que priorizan la integridad. Si hay un fallo de red, prefieren no responder. Ejemplo: **HDFS, MongoDB, Redis**.

AP

Disponibilidad + Partición

Sistemas que priorizan la respuesta. Garantizan el servicio con consistencia eventual. Ejemplo: **Cassandra, DynamoDB**.

La Realidad del Big Data

En sistemas de escala masiva, los fallos de red son inevitables. Por lo tanto, en la práctica, la Tolerancia a Particiones (P) es un requisito obligatorio. La verdadera decisión para un arquitecto de datos se reduce a elegir entre Consistencia (CP) o Disponibilidad (AP).
